## Decision drivers

1. **Truth must have one ledger — where truth exists.** For memory, rebuild outcomes are already durably recorded per (novelId, scope, sourceRevisionId) in `memory_projection` (OK/FAILED, attempts, lastError); a second mutable ledger for that same outcome invites divergence. For the seven named projections there is no outcome ledger at all today — no derived state exists to record outcomes for — so this driver binds only when (if) those projections gain pipelines.
2. **The write-side guarantee is real and must not regress.** C6 (atomic rebuild-intent commit; STORY-VERSIONING.md:386-410) is satisfied by construction — intents commit in the mutation transaction; Redis is never written at commit time. Both end-state options preserve this.
3. **Stale-read policy is enforced by derivation — for memory only.** C6's stale-read rule (STORY-VERSIONING.md:399-403) is met for memory by freshness derivation + UI labelling, with zero intent reads. For the seven named projections there is no derived read to protect; the C6 row itself (PENDING, never transitioned) is the only durable trace of their invalidation. This asymmetry is the honest statement of where the shipped model covers C6 and where it does not.
4. **Frozen-contract discipline.** STORY-VERSIONING.md is frozen; dispositions are recorded as dated amendments with review records (C12 precedent), never silent rewrites.
5. **Optionality for future projections.** All seven projections lack rebuild pipelines today. Whatever is decided must not make the wrong end-state expensive to reverse for canon/story-intelligence (or any other) pipelines when (if) they come to exist.
6. **The GAP-037-era evidence is current.** The re-verification confirms the no-consumer verdict stands after NF-WF-030/032/036, and after NF-WF-051's worktree implementation (which, like NF-WF-030, reuses `reconcileMemoryRebuilds` and never reads or writes DerivedRebuildIntent).

## Options

### Option A — per-projection intent consumers as each projection's rebuild pipeline comes to exist

Keep Invariant-4 sentence 2 as normative. When a projection's rebuild pipeline exists, that pipeline's worker consumes its own projection's PENDING rows: claim (CAS `PENDING → RUNNING` scoped to the projection), process, complete (`→ FRESH` with `completedAt`) or fail (`→ FAILED` with `lastError`, attempts incremented); a stuck-RUNNING reaper recovers crashed claims; an intent older than the branch head is consumed as stale-discard rather than rebuilt.

Consequences:

- **Positive.** Fulfills Invariant-4 sentence 2 literally; intents become an edge-triggered dispatch record at exactly the revision that invalidated the projection; a future projection could dispatch without a staleness scan; the schema's existing columns acquire meaning with no migration.
- **Negative.** For the only pipeline that exists (memory), a consumer adds nothing: it would re-derive exactly what NF-WF-030 startup reconciliation derives (STALE/FAILED scan against the head), while memory has no projection name to claim by (Q2) — a memory consumer would need either a new `memory` projection value (contract change) or a non-projection claim rule. It introduces the platform's first claim/lock machinery (per-projection ownership, CAS transitions, stuck-RUNNING recovery, consumer identity) that nothing else uses. For memory specifically it splits one truth across two ledgers (`memory_projection` outcome vs intent status) and needs code to keep them consistent, or explicit rules for which wins. Crash recovery becomes two-layered where only me…
- **Cost if chosen later.** Not foreclosed by Option B: the audit rows remain (projection, sourceRevisionId) pairs with the revision chain intact, so a future consumer ADR can supersede this one per projection. What is lost by waiting is nothing: no pipeline is blocked today, and all seven are in the same position.

### Option B — amend the audit role: intents stay write-side durable invalidation audit (recommended)

Declare the shipped model the end-state: `DerivedRebuildIntent` is the write-side, transactional, append-only record of *which projections a committed revision invalidated* (the C6 guarantee), not a work queue. Consumption, staleness and failure live where they are implemented today — which, stated precisely, means: for memory, head-derived freshness, FAILED projection rows, BullMQ dedup, reconciliation; for the seven named projections, nothing beyond the intent rows themselves, and no lifecycle claims are made for them. Concretely, without touching intent code:

- **Amend the C6/C7 records** (STORY-VERSIONING.md, dated amendment with review record per the C12 precedent — never a silent rewrite): sentence 2 of the 009 Invariant 4 is superseded — intent rows are not transitioned by workers for any projection; sentence 1 (logical staleness via derivation) is the normative invalidation semantics **for projections that have derived state (today: memory only)**. C6's bullet list is annotated: PENDING is terminal for audit rows; dedup `skipDuplicates` is the whole of replay idempotency.
- **Fix the schema comments** (schema.prisma:2579-2581 mutable-columns note and the model docstring at 2851-2852): mark `status/attempts/lastError/completedAt` as reserved-for-future-pipelines / audit-inert, PENDING as the assigned-and-final value. Comment-only change; no migration.
- **Keep the atomic commit exactly as is.** The C6 write-side guarantee (mutation + intents in one transaction) is unchanged — that is the part of the original design that works and is load-bearing.
- **Restore needs nothing.** OPERATIONAL classification (restore-scope.ts:113) already treats intents as never-rewound audit; the restore preview's "derived state requiring rebuild" reporting continues to come from impact analysis, not intent rows.

Consequences:

- **Positive.** Documentation and schema comments stop describing a lifecycle that never runs (the current stale-as-written comments are a standing trap for the next implementer). For memory: one ledger of rebuild truth (`memory_projection`); no claim/lock machinery to design, test, or operate; the memory reliability model — derivation, FAILED persistence, dedup, reconciliation — is shipped and reviewed. Zero code change; the only artifacts are contract amendment text and comment edits.
- **Negative.** C6/C7 contract text changes (frozen-contract amendment procedure owed, including a review record). The words "intent" and the unreachable RebuildStatus values (RUNNING/FRESH/STALE) remain as historical vocabulary unless a later additive migration prunes them (cosmetic; not required). Future projections lose the *option* of edge-triggered dispatch from these rows only until a superseding ADR — the rows themselves remain usable evidence of what invalidated what. For the seven named projections, Option B leaves exactly what exists today (an audit row and nothing else); it does not create stale-read or rebuild guarantees where none exist, and this ADR must not be cited as if it did.
- **Paired follow-up (worktree-implemented, pending main integration).** NF-WF-051 (memory reconciliation interval sweeper) closes the startup-only gap so the shipped memory model covers crash-without-restart, matching the workflow/publication recovery posture. Implementation lives in `.nf-batch-worktrees/scopeB-memsweeper` (reviewed APPROVE / AWF 2 Minor); integrating it to main is ordinary merge work, not a new design. Under Option B this is the remaining real work; it touches `packages/memory/src/constants.ts` + `apps/worker/src/memory-jobs.ts` only, never DerivedRebuildIntent.

## Decision (recommendation — the author decides)

**Recommend Option B.** For memory, the shipped head-derived staleness + reconciliation model has absorbed the table's intended function; a consumer that re-derives what reconciliation derives adds machinery without adding information, and memory cannot even be named as a projection to claim (Q2). For the seven named projections, no pipeline exists to consume anything, so the audit role costs nothing they currently use. This recommendation is grounded per-projection in the evidence table above; it is a recommendation only — both options remain open pending author decision. Atomic rebuild-intent commit stays exactly as implemented. Option A remains open per-projection via a future superseding ADR if a real pipeline wants edge-triggered dispatch. Note the corr…

## Alternatives

- **Option A (per-projection consumers)** — rejected for now: no pipeline needs it (all seven confirmed absent), memory has no projection name to claim, it duplicates memory reconciliation's trigger with a second ledger, and it introduces the platform's first claim/lock/reaper mechanism for zero behavioral gain. Re-open per projection when a pipeline exists that can name its projection and benefits from edge-triggered dispatch.
- **Delete the table** — rejected: the rows are transactional audit evidence of invalidation (restore keeps them OPERATIONAL deliberately), deletion is a destructive migration, and C6's write-side guarantee is worth keeping exactly as built.
- **Half-measures (move intents to Redis, or a generic consumer that transitions all projections)** — rejected: Redis-at-commit is forbidden by C6 and ADR-0014; a generic consumer violates per-projection ownership and would move rows for pipelines that do not exist.

## Consequences and verification

- Positive: honest docs (per-projection claims now match code); single source of truth for memory rebuild outcomes; no new runtime machinery; C6 atomicity preserved untouched.
- Negative: frozen-contract amendment procedure owed (C6/C7 records + schema comments); the unreachable enum values persist unless pruned later; the seven named projections remain with no stale-read or rebuild guarantees — documented as such, not assumed away.
- Follow-ups: (1) record the C6/C7 amendment with its review record; (2) fix the two schema comments; (3) integrate NF-WF-051 from `.nf-batch-worktrees/scopeB-memsweeper` to main (already reviewed APPROVE / AWF 2 Minor); (4) close the GAP entry's "NEXT: either implement platform-wide intent consumption … or amend the 009 contract text" decision point with this ADR's acceptance.
